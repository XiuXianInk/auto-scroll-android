# 架构说明

## 模块职责

| 类 | 职责 | 依赖 Android |
| --- | --- | --- |
| `ScrollService` | 无障碍服务本体：调度手势、维护滚动状态、响应屏幕与应用切换 | 是 |
| `ScrollMath` | 纯计算：给定速度算出每段的起点、终点、时长 | 否 |
| `ScrollPolicy` | 纯判断：此刻该不该滚 | 否 |
| `FloatPanel` | 悬浮球的绘制、拖动、淡出 | 是 |
| `MainActivity` | 设置界面与权限引导 | 是 |
| `PreviewActivity` | 内置预览页，含样例文本 | 是 |
| `Prefs` | 参数持久化 | 是 |
| `UiKit` | 颜色、圆角、字重等界面基础件 | 是 |

`ScrollMath` 和 `ScrollPolicy` 不引用任何 Android API。速度是否恒定、位移是否够大、该不该滚，这些判断最容易出错，一旦引入 Android API 就没法在 JVM 上测。

早期版本把这段计算直接写在 `ScrollService` 里，验证时只能复制一份出来跑——那验的是副本，改完可能不同步。抽出来之后，测试编译的就是运行时那份类文件。

## 一次滚动的时间线

```
startScroll()
  running = true，申请 WakeLock
  pump()
    ↓
  ScrollMath.compute() → (startY, endY, durationMs)
  构造 GestureDescription，dispatchGesture()
    ↓ 系统执行手势，手指从 startY 滑到 endY
  onCompleted()                        ← 手势完成
    inFlight = false
    handler.post(pumpTask)             ← 投到队列末尾，不在回调栈里直接注入
    ↓
  pump() 再次计算并下发下一段
```

两个实现细节：

**不在 `onCompleted` 里同步下发下一段。** 回调触发的那一瞬，上一段占用的输入资源可能还没释放，紧接着的注入会被系统拒绝。投递到消息队列末尾多花约一帧，换来明显更高的衔接成功率。

**回调要做身份校验。** 停止后立刻重启时，上一段的回调可能迟到，如果照单全收会把新段的 `inFlight` 清掉，于是下一段被放行——两段手势同时下发，速度直接翻倍。所以每段下发前把 `GestureDescription` 存进 `currentGesture`，回调里比对 `gestureDescription != currentGesture` 就丢弃。

## 状态

| 字段 | 含义 | 谁改 |
| --- | --- | --- |
| `running` | 用户是否要求滚动（不代表此刻真的在滚） | `startScroll` / `stopScroll` |
| `inFlight` | 有一段手势正在执行 | `pump` / 回调 |
| `currentGesture` | 当前这段的标识，用于丢弃过期回调 | `pump` |
| `screenOn` | 屏幕是否点亮，熄屏时暂停注入 | 广播接收器 |
| `previewMode` | 是否在预览页，跳过所有滚动限制 | `PreviewActivity` |
| `currentPkg` | 当前前台应用包名 | 无障碍事件 |

`running` 与 `inFlight` 是两件事。用户点了开始，但如果当前在别的应用、屏幕已熄或用户正按着屏幕，`running` 仍为 true 而实际没有手势在跑——回到目标应用后会自动续上，不需要重新点开始。

## 为什么是这些参数

**每段位移约 1/4 屏、时长 1.5～6 秒。** 段长同时被三件事拉扯：越长越顺滑（抬手次数少）、越长暂停越迟钝（手势不可撤销）、太短则位移不够。折中点是让位移固定、时长随速度反推，这样速度恒定，而段长在合理区间内浮动。

**位移下限 32dp。** 系统 touch slop 约 8dp，低于它的手势会被判成点击，反而触发目标应用自己的点击翻页或菜单。极慢速时按比例延长段长来保住位移，代价是那一段变长，但速度不变。

**退避从 16ms 递增到 512ms，连续失败 6 次后拉长到 1 秒。** 前几次失败通常是资源未释放，帧级等待就够；连续失败说明屏幕正被用户操作，这时候继续硬顶只会和用户抢手势，不如退到每秒一次。

**60 分钟硬上限。** 滚动期间持有 WakeLock，如果用户睡着，屏幕会一直亮、手势一直发。这是防烧屏和耗电的兜底，不是功能。

## 测试策略

分三层，覆盖的东西不一样：

| 层 | 手段 | 能验证什么 | 验证不了什么 |
| --- | --- | --- | --- |
| 逻辑 | JUnit，直接跑 `ScrollMath` / `ScrollPolicy` | 速度恒定性、位移下限、映射单调性、判断分支 | — |
| 界面 | Robolectric，实例化 Activity | 能否创建、文案是否齐全、布局几何、生命周期 | 真实字体渲染、真实手势 |
| 静态 | Android Lint | API 级别、权限声明、资源引用 | 运行时行为 |

Robolectric 的两处限制：

- **没有真实字体**，文本宽高测出来是 0 或固定值，任何依赖字号的断言都不可信。布局测试只验证几何（位置、是否溢出、是否重叠），不验证文字尺寸。
- **`scrollTo()` 只改字段，不触发 `onScrollChanged`**。所以「滚到底」的判定逻辑抽成 `ScrollMath.isScrolledToBottom` 单独测，UI 联动用反射直接触发回调验证。

## 已知的边界

- 注入的是真实触摸事件，与用户手指操作互斥，无法做到完全并行
- 无障碍服务读不到其他应用的滚动位置，「到底了」判断不了
- 手势一旦下发不可撤销，暂停必然有延迟
- `continuedStroke` 续接可以实现无缝衔接与即时暂停，但续接超时会让手指挂住触发长按选词，尚未采用（见 README 路线图）
